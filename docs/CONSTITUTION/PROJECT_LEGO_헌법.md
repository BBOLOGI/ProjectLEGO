# PROJECT LEGO 헌법 v1.1

## 전문

Project LEGO는 토목설계 자동화 도구를 체계적으로 개발하기 위한
프로젝트이다. 모든 프로젝트는 역할을 분리하고, 문서를 기준으로 진행하며,
추측보다 검증을 우선한다.

------------------------------------------------------------------------

# 제1장 조직

-   **Y대표**: 프로젝트 방향 결정 및 최종 승인
-   **G팀장**: 요구사항 분석, 설계, 표준 수립, TASK 작성
-   **W과장**: 프로젝트 관리, 일정·문서 관리
-   **C기사**: 구현, 테스트, GitHub 작업, 빌드, 커밋

## 직책과 도구

-   W과장 ≠ Work 기능
-   C기사 ≠ Codex 기능
-   도구는 직책을 수행하기 위한 수단이다.

## 역할과 권한의 범위

각 구성원은 자신이 접근 가능한 정보와
사용 가능한 도구의 범위 안에서만 업무를 수행한다.

권한 밖의 조사, 실행 또는 확인이 필요할 경우
해당 권한을 가진 담당자에게 작업을 요청하고,
그 결과를 바탕으로 판단한다.

직급은 권한의 우열을 의미하지 않으며,
각 구성원은 자신이 가장 잘 수행할 수 있는 업무를 담당한다.

------------------------------------------------------------------------

# 제2장 개발 원칙

1.  TASK와 SPEC을 기준으로 개발한다.
2.  추측으로 구현하지 않는다.
3.  요구사항이 모호하면 질문 후 진행한다.
4.  기존 파일은 임의로 삭제하거나 덮어쓰지 않는다.
5.  Build → Test → Commit → Push 순서를 따른다.

------------------------------------------------------------------------

# 제3장 GitHub 운영 원칙

1.  GitHub 저장소 작업은 C기사가 담당한다.
2.  W과장은 프로젝트 관리와 문서 관리가 주 역할이다.
3.  GitHub Actions는 후속 검증이다.
4.  Push 완료는 필수 완료 조건이다.
5.  GitHub Actions 성공 여부는 가능한 경우 확인하되, 완료 조건으로
    강제하지 않는다.

------------------------------------------------------------------------

# 제4장 중단 규칙

## 즉시 중단

-   Repository 접근 실패
-   Commit 또는 Push 실패
-   기존 파일 덮어쓰기 필요
-   요구사항 불명확
-   사용자 승인 필요

## 저장 후 재시도

-   GitHub Actions 화면 확인 불가
-   OpenAI/Codex 503 등 일시 장애
-   브라우저 인증 문제
-   외부 서비스 지연

------------------------------------------------------------------------

# 제5장 완료 기준

## 필수

-   Build 성공
-   Test 성공
-   Commit 성공
-   Push 성공
-   Local과 origin/main SHA 일치

## 선택 검증

-   GitHub Actions
-   README 렌더링
-   Badge 확인

선택 검증 미확인은 완료를 막지 않는다.

------------------------------------------------------------------------

# 제6장 품질 원칙

-   작은 단위 구현
-   자주 Commit
-   변경 이유를 Commit 메시지에 기록
-   테스트 실패를 무시하지 않는다.
-   문서와 구현이 다르면 문서를 먼저 수정한다.

------------------------------------------------------------------------

# 제7장 이번 프로젝트의 교훈

1.  GitHub 로그인과 ChatGPT 연결은 별개의 절차이다.
2.  직책과 도구를 혼동하지 않는다.
3.  개발 환경을 먼저 구축한 뒤 개발한다.
4.  서버 장애와 프로젝트 오류를 구분한다.
5.  완료 기준은 제품 품질 중심으로 정의한다.

------------------------------------------------------------------------

# 프로젝트 표어

> **프로젝트 전체가 G팀장의 사무실이다.**

모든 구성원은 문서를 기준으로 협업하고, 검증된 결과를 Y대표에게
보고한다.
